# 작업 지침

이 폴더는 기획자의 웹게임 작업 폴더다. 사용량을 아끼는 것도 결과물 품질만큼 중요하다.

## 작업 방식
- 답변은 무조건 한국어 존댓말로 하고, `~입니다` 말투를 쓴다. 쉬운 말로 짧게, 바뀐 것과 기획자가 할 일만 말한다.
- 앱(웹게임) 테스트는 기획자가 직접 한다. 직접 실행하거나 테스트하지 않는다.
- 필요한 경우에만 서브에이전트를 쓴다. 서로 독립된 큰 작업일 때만 쓴다.
- 화면 디자인은 `apple-design` 스킬을 따른다.

## 읽기
- 이미 읽은 파일을 통째로 다시 읽지 않는다. 바뀐 내용은 `git diff`로만 확인한다.
- 기획서가 필요하면 `Docs/기획서_요약.md`를 먼저 보고, 필요한 문서의 필요한 부분만 `Docs/Notion/`(노션 싱크 결과)에서 읽는다.
- 노션은 MCP로 읽거나 화면을 캡처해서 읽지 않는다. 최신본이 필요하면 "노션 동기화" 버튼을 눌러 달라고 한다.
- 노션 쓰기(Notion MCP)는 "노션에 반영" 요청이 있을 때만 하고, 바뀐 부분만 반영한다.

## 만들기
- 밸런스·확률 같은 시뮬레이션은 실행 가능한 스크립트로 만들어 돌리고 결과 숫자만 보고한다. 항목마다 에이전트를 띄워 머리로 추론하지 않는다.
- 조정할 수치는 데이터 파일 하나(예: `balance.json`)에 모아 기획자가 직접 고칠 수 있게 한다.
- 결정한 내용은 기획서·코드 파일에 남긴다. 다음 작업은 새 세션에서 이 파일들을 읽고 이어 간다.

## 프로토타입(웹게임·인터랙티브 기획서)을 만들 때
- 프로토타입은 기획을 확인하는 도구다. 완성도보다 "기획 의도를 빨리 확인할 수 있는가"를 먼저 본다.
- 시스템마다 짧은 영문 id를 붙이고(예: `fight1`, `mon4`), 기획서 제목·화면 구획 앵커(`#fight1`)·코드 파일·데이터 키에 같은 id를 쓴다. 기획서, 프로토타입, 개발용 문서가 id 하나로 이어지게 한다.
- 수치(속도, 쿨타임, 판정 범위 등)는 `data/<id>.json`에 둔다. 코드에 숫자를 직접 쓰지 않는다.
- 화면에 수치 조정 패널(슬라이더)을 두어 기획자가 플레이하면서 바로 바꾸게 하고, "JSON 복사" 버튼으로 결과를 데이터 파일에 붙여 넣게 한다. 수치 조정에 AI를 쓰지 않게 하기 위해서다.
- 판정과 타이밍(피격 판정 시점, 쿨타임, 히트박스)은 디버그 표시로 화면에 보이게 하고, 켜고 끌 수 있게 한다. 애니메이션과 판정이 어긋나면 바로 보이도록.
- 단위는 기획서와 같은 단위(초, px, 칸)를 쓰고, 개발용 변환에 쓸 단위 환산 비율도 데이터 파일에 함께 둔다.
- 버전은 파일을 복사해 늘리지 말고 git 커밋으로 남긴다. 공유 링크의 버전과 커밋을 맞춘다.
- 판정·수치 계산은 짧은 스크립트 테스트로 확인하고, 화면 캡처로 확인하지 않는다. 손맛 확인은 기획자가 직접 플레이해서 한다.
- 개발용 기획서로 바꿀 때는 시스템 id별로 목적, 상태와 전환, 입력, 수치 표(데이터 파일 기준), 예외 상황을 적는다.

## 개발 저장소에서 작업할 때
- 그 저장소의 `CLAUDE.md`와 기존 코드 규칙을 먼저 따른다. 이 지침은 그다음이다.

## Git
- git 커밋·푸시는 "작업 커밋" 요청이 있을 때만 한다. 중간에 스스로 커밋·푸시하지 않는다.
- 커밋하기 전에 반드시 현재 변경된 파일과 diff를 확인한다.
- 요청과 관계없는 변경사항이 포함되지 않았는지 확인한다.
- 사용자가 작성했거나 다른 개발자가 작업 중인 변경사항을 임의로 커밋하지 않는다.
- 요청과 관련된 변경사항만 커밋한다.
- 커밋 메시지는 짧은 한글로 작성하며 변경 종류에 따라 앞에 다음 접두사를 붙인다.
- 커밋 메시지에 `Co-Authored-By` 트레일러를 추가하지 않는다.

* `add:` 새로운 기능이나 파일 추가
* `edit:` 기존 기능이나 파일 수정
* `fix:` 버그 수정
* `remove:` 기능이나 파일 제거

예시:

* `add: 상호작용 시스템`
* `edit: 플레이어 이동`
* `fix: 아이템 중복 획득`
* `remove: 미사용 테스트 코드`

- push 전에 원격 변경사항으로 인해 충돌 가능성이 있는지 확인한다.
- 다른 개발자의 원격 변경사항이 존재하면 이를 덮어쓰지 않는다.
- 필요하다면 현재 브랜치와 원격 브랜치의 차이를 먼저 확인한다.
- force push를 사용하지 않는다.
- 사용자가 명시적으로 요청하지 않는 한 다음과 같이 다른 사람의 작업을 잃을 가능성이 있는 명령은 사용하지 않는다.

* `git reset --hard`
* `git clean`
* `git checkout -- <file>`
* `git restore`를 이용한 기존 변경사항 제거
* force push
* 다른 사람의 커밋이나 작업 내용을 임의로 되돌리는 명령

- 충돌이 발생하거나 원격 변경사항 때문에 안전하게 push할 수 없다면 기존 작업을 덮어쓰지 않는다.
