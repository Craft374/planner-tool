# 개발 작업 지침

이 PC에서 이 저장소를 개발할 때 쓰는 개인 지침이다. 저장소의 `CLAUDE.md`와 기존 코드 규칙이 먼저이고, 이 지침은 그 위에 더한다. 둘이 다르면 저장소 쪽을 따른다.

## 작업 방식
- 답변은 한국어 존댓말, `~입니다` 말투로 짧게 한다. 바뀐 파일과 확인할 것만 말한다.
- 에디터·게임 실행과 실제 테스트는 개발자가 직접 한다. 임의로 실행하지 않는다.
- 큰 변경은 먼저 계획(바꿀 파일, 순서, 위험한 부분)을 보여 주고 승인받은 뒤 고친다.
- 서브에이전트는 서로 독립된 큰 작업에만 쓴다.

## 사용량 아끼기
- 이미 읽은 파일을 통째로 다시 읽지 않는다. 바뀐 내용은 `git diff`로만 확인한다.
- 큰 파일은 필요한 부분만 찾아 읽는다(검색 후 해당 줄 근처만).
- 생성 폴더(Unity라면 `Library/`, `Logs/`, `Build/`, `Temp/`, `obj/`)는 읽지도 고치지도 않는다.
- 로그는 끝부분에서 오류·예외만 골라 읽는다. 로그 전체를 읽지 않는다.

## 기획과 연결
- 기획서는 `Docs/Notion/`(노션 싱크 결과)에 있다. 노션을 MCP로 읽거나 화면을 캡처하지 않는다. 최신본이 필요하면 "노션 동기화" 버튼을 눌러 달라고 한다.
- 기획서·프로토타입에 시스템 id(예: `fight1`, `mon4`)가 있으면 코드 클래스·데이터 키·커밋 메시지에서 같은 id로 찾을 수 있게 한다.
- 기획 수치는 코드에 직접 쓰지 말고 데이터(ScriptableObject, JSON 등)로 뺀다. 기획서의 단위(초, px, 칸)와 엔진 단위의 환산은 한곳에서만 한다.

## Git
- git 커밋·푸시는 "작업 커밋" 요청이 있을 때만 한다. 중간에 스스로 커밋·푸시하지 않는다.
- 커밋하기 전에 반드시 현재 변경된 파일과 diff를 확인한다.
- 요청과 관계없는 변경사항이 포함되지 않았는지 확인한다.
- 사용자가 작성했거나 다른 개발자가 작업 중인 변경사항을 임의로 커밋하지 않는다.
- 요청과 관련된 변경사항만 커밋한다.
- 커밋 메시지는 짧은 한글로 작성하며 변경 종류에 따라 앞에 다음 접두사를 붙인다.
- 커밋 메시지에 `Co-Authored-By` 트레일러를 추가하지 않는다.

* `add:` 새로운 기능이나 파일 추가
* `edit:` 기존 기능이나 파일 수정
* `fix:` 버그 수정
* `remove:` 기능이나 파일 제거

예시:

* `add: 상호작용 시스템`
* `edit: 플레이어 이동`
* `fix: 아이템 중복 획득`
* `remove: 미사용 테스트 코드`

- push 전에 원격 변경사항으로 인해 충돌 가능성이 있는지 확인한다.
- 다른 개발자의 원격 변경사항이 존재하면 이를 덮어쓰지 않는다.
- 필요하다면 현재 브랜치와 원격 브랜치의 차이를 먼저 확인한다.
- force push를 사용하지 않는다.
- 사용자가 명시적으로 요청하지 않는 한 다음과 같이 다른 사람의 작업을 잃을 가능성이 있는 명령은 사용하지 않는다.

* `git reset --hard`
* `git clean`
* `git checkout -- <file>`
* `git restore`를 이용한 기존 변경사항 제거
* force push
* 다른 사람의 커밋이나 작업 내용을 임의로 되돌리는 명령

- 충돌이 발생하거나 원격 변경사항 때문에 안전하게 push할 수 없다면 기존 작업을 덮어쓰지 않는다.
